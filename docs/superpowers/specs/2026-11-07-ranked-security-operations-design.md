# Ranked security, connection and operations design

**Status:** Proposed technical defaults for owner review in PR #29, November 7, 2026. Not implemented or operationally verified. Approved competition policies remain in [[2026-11-07-ranked-decision-record]]. This document fills Q8/Q10/Q11/Q12 implementation choices; it does not silently approve content, buy services or authorize publication.

## Intent, constraints and approaches

Build a small, understandable employee pilot on the existing Windows 11 / 16 GB machine, with 30 simultaneous players as a validation target. Preserve current Practice and the live Pages site. No multiplayer, hidden rating, automatic cheating penalties, new administrator history access or routine score edits.

Considered: (1) existing FastAPI plus local PostgreSQL and server sessions; (2) managed identity/database/hosting, which reduces operator work but adds vendors, migration and spending; (3) public router port forwarding, which adds home-network exposure and certificate/ingress maintenance. **Assistant recommendation: option 1, with a tunnel for eventual public ingress.** The owner has delegated technical drafting; these choices remain reviewable proposals, not previously approved owner statements. No packages or infrastructure are created by this PR.

## Q8 — original session, loss detection and deadlines

- Use an authenticated persistent connection plus a server heartbeat every one second while an attempt is active, including feedback. Declare a loss on transport close or after three seconds without an authenticated heartbeat response. These cadence numbers are assistant defaults. Start the approved 15-second grace at that server declaration, not at the unknowable instant Wi-Fi failed. Keep one loss ID per uninterrupted loss; repeated failed requests do not create flags.
- A return strictly before the grace deadline may restore only the original still-running page instance. At or after the deadline, finalization wins. Recovery never restarts question clocks or extends grace. A later, genuinely distinct loss after recovery receives a new loss event, subject to approved flag rules.
- Bind the attempt to a random page-instance capability generated by the server and held only in that page's memory. Do not persist it in browser storage, cookies, URLs or logs. Authenticate both account session and capability on connection/answer/Next requests. An ordinary login cookie or knowledge of attempt ID cannot resume it after reload or from a second tab. Keep the account-level active-attempt lock throughout grace. A pending start response lost during reload cannot create another attempt; reconcile as active and let the original loss policy terminate it.
- This enforces page-session possession, not proof of physical hardware or human intent. A malicious user can copy secrets from their own running browser; do not claim fingerprinting or perfect device enforcement. Refresh detection is best effort through connection/heartbeat loss, never an extra Quit penalty.
- Keep one server-owned current question and deadline, a monotonic per-attempt sequence, immutable answer acceptance and transactional idempotency keys. Normal/promotion Next requests activate only the next question once; final answer/timeout settles without Next. Tie-break advancement is automatic, with no player feedback pause.
- **Owner timing decision (November 7): start the server deadline when the server first sends that question's content.** No client acknowledgment gates activation or grants extra thinking time. Record one first-send timestamp/deadline per question, atomically with its sequence; retries resend the same question with the same deadline. Never send plaintext question content before activation. Tie-break transition automatically activates/sends the next question once; ordinary/promotion Next does so on the accepted Next request.
- **Approved delivery tradeoff:** a question sent just as the connection fails may never appear and can still time out. Questions never sent receive no deduction. Do not equate a successful server write with guaranteed browser receipt; do not promise zero unseen timeouts. If loss is already known, send no next question; a race between sending and observing loss is covered by this approved tradeoff. Current issued-question deadlines continue through grace, with no retransmission reset. Test first-send/answer/timeout/disconnect races, lost delivery and late/duplicate messages.
- Serialize answer, timeout, Quit, loss expiry, season cutover and round invalidation. Repeated terminal requests return the same terminal state and apply points at most once. A late answer cannot resurrect a terminal attempt. Tie-break APIs withhold correctness, score, answer keys and review until the valid round deadline.
- A client report never establishes a server-wide outage. Use trusted service lifecycle/health evidence: API process epoch change, database unavailability or confirmed public-route failure from independent probes. Persist attempt/round ownership and outage intervals. API restart or a confirmed service-wide interruption invalidates affected active normal/promotion attempts with zero adjustment and no flags; the interrupted tie-break round restarts for everyone, including completed players, with a fresh set/window. Preserve earlier valid rounds.
- Use a terminal-but-settlement-pending state while common-outage classification is unresolved. Keep the account admission lock: do not apply a provisional balance, start a new Ranked attempt, promote/demote or finalize affected prizes. Trusted observers must provide an evidence watermark covering the attempt loss/termination interval before classification commits. An unavailable/lagging observer holds settlement pending rather than declaring a personal failure. Commit the final outage or personal-loss outcome and balance once, then release admission. This avoids undoing caps/promotions after later play. No automatic reversal of committed balance or downstream replay is introduced. Test observer delay, process epoch changes and missing evidence; if the deployed monitoring cannot establish that evidence boundary, public Ranked remains disabled until the protocol is reviewed. Keep client-local failures distinct from confirmed common failures. External probe location and classification tests are release gates in #13; `/health` alone is not such monitoring.

## Q10 — authentication and recovery

Use existing FastAPI with vetted password hashing through `pwdlib[argon2]`, following [FastAPI's password-hashing guidance](https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/). Prefer opaque server-side sessions stored in PostgreSQL over browser-held JWTs for this pilot. Pin compatible libraries only during reviewed implementation, and benchmark hashing on the real Windows machine.

Assistant defaults:

- Username: 3–24 ASCII letters, digits or underscore; case-insensitive uniqueness and login, reserve admin/support/system names. Stable internal UUID and unique six-character uppercase alphanumeric tag; supported rename preserves ownership, tag and eligibility. These format restrictions are proposals, not earlier owner decisions.
- Password: 15–128 characters, allow spaces/Unicode/paste/password managers, no composition rules or scheduled forced changes. Reject common/compromised choices using a maintained local blocklist without sending a player's password externally. Bound request sizes before hashing; rate-limit per account and network without permanent automatic lockouts. Exact throttling/Argon2 cost is benchmarked in #7. See [OWASP authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html).
- Production session cookie: host-only, Secure, HttpOnly, SameSite=Lax, Path=/; no session tokens in localStorage. Server-enforced 30-minute idle / eight-hour absolute lifetime, rotation on login or privilege changes, revocation on logout/recovery/password change. Active quiz traffic counts as activity. Warn before expiry; expiry uses existing loss handling, with same-page reauthentication permitted only within existing grace, never a fresh-page resume. Server authorization is required on every object operation. See [OWASP sessions](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).
- Same-origin production frontend/API. Validate Host/Origin and use CSRF protection for cookie-authenticated writes, including login, recovery handoff, deletion and owner actions. SameSite alone is insufficient. Development CORS remains an explicit loopback allowlist; never wildcard credentials. See [OWASP CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).
- Generate session/reset/capability secrets with a vetted cryptographic generator, e.g. explicit 32 random bytes via [Python secrets](https://docs.python.org/3.14/library/secrets.html); store token digests and never log raw secrets. One-use email verification/reset links expire after 15 minutes, bind account/purpose/current destination version, and invalidate on replacement, email change/removal, password recovery or deletion. Generic request responses prevent account enumeration; never auto-login after recovery. See [OWASP recovery](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).
- Email stays optional/private. Permit only one active verified recovery account per normalized address; preserve provider-specific dots/+aliases rather than guess equivalence. Keep the old verified address until a new one is verified; require recent reauthentication, revoke old destination tokens and cancel old queued reminder mail on switch/removal. Email verification does not grant prize eligibility or reminder consent.

**New owner decision:** Without verified email, require in-person verification with Renilson at work, matched to a participant/account link confirmed before the request. Username/tag knowledge alone never qualifies. No verified email and no trusted prior link means no reset. Recovery restores only the existing account, never wiped data or a substitute prize account.

Proposed manual flow: logged-out Support offers a rate-limited recovery request for the public account identifier and a random private request code. Renilson verifies the person and pre-existing link in person; only the authenticated owner can approve that specific short-lived request. Approval issues a single-use 15-minute handoff for setting a new password privately. It does not expose the old password, log in the owner as the player or grant history access. No sensitive evidence uploads or security questions. Reject replay, changed account/request binding and expired handoffs; revoke prior sessions/tokens on completion.

Bootstrap the sole owner role using a one-time local operator command, never a public signup flag. Require vetted MFA and recent reauthentication for owner eligibility/recovery/prize actions; select/pin the MFA component in #7. Owner recovery uses a documented local operator procedure with offline recovery material. No other administrator gets prize-approval/recovery authority or private Pre-Season history. Confirmed credential compromise can revoke sessions; connection flags alone never authorize suspension. A disciplinary account-ban feature is not part of this decision.

## Q10 — deletion, minimum marker and races

- Require current-password reauthentication within five minutes, CSRF protection, account ownership and the approved explicit unchecked acknowledgment/final Delete action. Cancel is available before final submission; after the server accepts the irreversible authorized deletion there is no undo or restoration. Invalid/unauthorized requests roll back without withdrawal. Do not treat a lost browser response as permission to repeat withdrawals or reopen the account.
- Serialize acceptance with prize finalization using the same season/account transaction boundary. Accepted deletion before prizes finalize withdraws the candidate and creates the sole approved season-ineligibility marker; an already finalized award is not clawed back. Repeated deletion/finalization messages cannot award twice or withdraw another player.
- At acceptance revoke sessions/reset/verification links, cancel queued mail, end the active attempt without preserving its account-owned score/history, and remove the candidate from prize selection. Do not fabricate an extra Quit score or affect other players' points. The account becomes inaccessible and deletion remains **pending** until every managed purge finishes. Show completed only after verified primary/provider/backup erasure. A cleanup failure is pending work, never a reason to restore account access or silently claim completion.
- Wipe profile/contact/credentials, all account-owned attempts/answers/score/history including Pre-Season, personal tickets/flags/connection details, pending email payloads and account links. Preserve other players' records and shared question versions. Redact/unlink the deleted player's detail from shared evidence, without retaining a deleted-player shadow record. Ordinary 15-day case retention never overrides this wipe.
- Minimal marker fields: **owner-recognizable private roster reference, season ID, ineligible state and expiry at global prize finalization**. The owner explicitly approved this recognizable reference on November 7 because a random code alone cannot identify a returning person. No former account ID/tag/username/email, score, history or credential. During in-person eligibility review, Renilson matches the sorter to that pre-existing reference, checks the season marker, and denies same-season prize approval when ineligible. If continuity cannot be established, do not approve a replacement account. This is a small human-verified cohort process, not automatic real-person identification. While an account exists, its trusted participant/account link is owner-only; erase that account link at deletion, retaining only the approved minimal marker. Do not copy a roster/name list into a hidden profile or collect new documents. Delete the marker/reference at global prize finalization; it is never account-recovery authority.
- Backups must not resurrect deleted account data. Proposed small-pilot strategy: after purge, replace the controlled base backup/recovery chain with a verified clean generation, retire every older controlled snapshot/WAL copy containing the account, then verify the clean restore. Check disk snapshots, off-device storage, logs and provider previews as well as tables. Cleanup work may temporarily contain the identifiers it needs only while deletion is pending; it is not an additional completed-deletion retention exception. No permanent account deletion tombstone is authorized.
- Do not promise erasure of mail already in a recipient inbox or copies outside operator control. Provider retention and backup deletion must be proved before employee registration is enabled. If the actual backup/provider contract cannot satisfy the strict wipe rule, stop that integration and return the conflict for owner review; no quiet retention exception.

## Q11 — email adapter, budget and uncertain delivery

Use a local capture adapter with fictional recipients for development. Proposed public adapter: Brevo transactional email, **conditional** on deletion, sender verification and retry contract tests. No account, domain, credentials or paid service is provisioned here. Default spending limit is $0; any purchase/upgrade needs a separate owner decision. Keep contacts out of marketing lists and disable optional open/click tracking.

Rationale: [Brevo's free plan](https://help.brevo.com/hc/en-us/articles/208589409-About-Brevo-s-pricing-plans) documents 300 sends/day. Its [log deletion API](https://developers.brevo.com/reference/delete-an-smtp-transactional-log) removes logs and stored previews by message or address. By contrast, [Resend's retention guidance](https://resend.com/security/gdpr) documents retained email data and no individual-email deletion API; it is not the default for this strict wipe policy. Brevo's [deletion guide](https://developers.brevo.com/docs/deleting-transactional-logs-based-on-recipient-address-to) describes asynchronous processing whereas the reference shows 204: test the actual API and confirm completion/retention scope before enabling real mail. Log removal alone does not prove vendor-backup erasure.

- Use a durable application outbox with one logical message key, recipient/destination version, consent version, attempt counter and bounded worker lease. A retry uses the same provider UUID key and identical content. Rate-limit dispatch to one/second and at most 200 application emails/day, reserving 50 of that application budget for verification/recovery; quota exhaustion stops app dispatch rather than creating a provider backlog. Owner's other provider traffic must fit actual available quota. These are proposed safety defaults, not guaranteed capacity.
- Approved launch maximum stays initial send plus two retries within the first hour. Proposed retry times: initial, +1 minute, +5 minutes, subject to quota and provider backoff; stop at one hour even if fewer attempts occur. Never treat a timeout as proof that the provider rejected a message.
- Brevo documents a [30-minute idempotency lifetime](https://developers.brevo.com/docs/heterogenous-versions-batch-emails). Test the exact single-recipient request shape. Reuse the key only inside its confirmed validity window for an ambiguous send; reconcile through authenticated provider events/logs. A late ambiguous send beyond that window becomes delivery-unknown, with no blind resend/new key. Never claim provider-independent exactly-once delivery. Invalid/unverifiable webhooks must not mark success.
- Serialize send selection with opt-out/deletion/email-change and recheck immediately before dispatch. Cancel queued/unaccepted messages. A message already accepted or in flight cannot reliably be recalled; show that distinction. After launch retires the opt-in checkbox, profile Settings retains a pending-reminder status and Cancel pending reminder until acceptance/cancellation/exhaustion. It cannot renew consent or enroll another season. Final UI needs #16 mockup review.
- Purge account-owned outbox/logs/provider previews at deletion, with reconciliation of any in-flight send before completion. Do not retain the email/key as a hidden deleted-account record. Provider confirmation is acceptance, not proof of inbox receipt.

## Q12 — bank ownership and versioning

See [[2026-11-07-ranked-question-bank-review]]. Practice deck counts are candidate inventory, not approved Ranked difficulty labels or a guarantee of correct answers. Renilson reviews the actual Easy/Medium/Hard content and the separate Hard work-methods bank in #5.

Assistant defaults: one canonical scenario per unique service/destination/range/exception meaning, with one owner-approved answer, explanation and difficulty per immutable version. Equivalent wording/service aliases cannot create extra independent assignment slots. Resolve overlapping ranges and exception precedence with the owner rather than blindly merge them. No repeat canonical scenario within a 15-question assignment; require five approved unique questions per difficulty before starting. If insufficient, disable Ranked start with an explanation, no attempt or score; Practice remains open. The count/conflict inventory is only a heuristic and must be re-run after curation.

Tie-break rounds require five fresh approved Hard work-methods questions shared by the group. Track prior sets across valid and outage-replaced rounds; no silent reuse. If unavailable, follow approved owner-selection fallback. Freeze content/answer versions per assignment/round. Ordinary content corrections affect future assignments, not a silent retrospective rescore. Existing active version-error/void handling needs the reviewed #4/#5 acceptance examples; no routine admin answer/difficulty/point edits.

## Q12 — public hosting and operations

- Keep current Pages Practice unchanged. Propose a separate pilot hostname serving the reviewed frontend and `/api` from the Windows host, so authentication is same-origin. Serve an explicit build/static asset allowlist, never the repository root, backend source, `.git`, `.env`, virtual environment, local config, exports or backups.
- Use [Cloudflare Tunnel](https://developers.cloudflare.com/tunnel/get-started/) to reach loopback services without router port-forwarding. A suitable domain/account and tunnel setup are execution prerequisites, not already owned/provisioned facts. API/database stay private on loopback; no public PostgreSQL port. Tunnel is ingress, not an authorization substitute. Review proxy-trust scope, HTTPS, Host validation, secure cookies, CSP and CSRF with real production URLs before launch.
- Windows services run without an interactive terminal, restart on crash/boot, under least privilege; configure power/sleep, disk encryption, OS/dependency/tunnel updates and secret permissions. [Windows tunnel service documentation](https://developers.cloudflare.com/tunnel/features/locally-managed-tunnels/as-a-service/windows/) provides the supported service approach. Keep development/test/production configuration and databases separate.
- Select a supported PostgreSQL major and compatible Windows driver/migration tools in #6; exact installation/pins are not chosen from assumptions. Use transaction constraints, unique settlement keys, phase/round version guards and a durable outbox. Validate migration/rollback and backup restore before real user data. Integrity checks do not replace an actual restore; see [PostgreSQL backup verification](https://www.postgresql.org/docs/17/app-pgverifybackup.html).
- Proposed release acceptance: 30 simultaneous simulated players for 15 minutes; p95 quiz/control response <=1 second, no unexpected 5xx, cross-account access, duplicate settlement or deadline resets. Include login/hash load, cutover, concurrent deletion/prize finalization, service restart, database outage, internet loss, slow/background mobile tabs and reconnect at just-before/exactly/after grace. These are targets to measure, not results or a promise that 16 GB suffices.
- Proposed recovery targets for owner review before rollout: <=15 minutes accepted-data loss and <=one hour restoration. Measure them using a separate encrypted off-device backup plus a clean restore and the deletion-safe backup replacement procedure. Actual storage destination, retention/erasure capabilities, power/network reliability, monitoring and operator runbook remain #13 execution gates. Do not start employee registration until these gates and the strict wipe contract pass.
